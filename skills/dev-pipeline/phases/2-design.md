### 2. 設計（Design）

`.scratch/<issue番号>/requirements.md`を指し示して、subagent_type `software-architect`を呼び出す。`.scratch/<issue番号>/design.md`に書き込まれる。

**設計レビュー。** 続いて、「レビュー省略の判定」を設計に適用する。条件は、影響を受けるファイルが3つ以下、DBスキーマ・マイグレーション・APIコントラクトの新設や変更がない、`requirements.md`の受け入れ基準が3件以下、の3点を**すべて**満たすこと。省略しない場合は、`.scratch/<issue番号>/requirements.md`と`.scratch/<issue番号>/design.md`を指し示してsubagent_type `design-reviewer`を呼び出す。`.scratch/<issue番号>/design-review.md`に書き込まれる。

レビュアーはACマッピングの網羅性、APIコントラクトとDBスキーマ・データモデルの具体性、影響を受けるファイルの実在、既存の抽象化への適合、ステップの順序、リスクの見落とし、スコープの逸脱、configの設計ルールが追加で要求する事項を確認する。見つけたものをすべて報告し、各指摘に**要修正** / **任意** / **確度低**のタグを付ける。フィルタリングを担うのはあなたである。

- 要修正の指摘がある場合は、`software-architect`を**修正モード**で呼び出す（任意の指摘だけの場合は呼び出さない。設計書のパスとレビューレポートのパスを渡す。言い換えない）。その後、反映した指摘がすべて軽微な文書修正（誤字、用語の不統一、参照の誤り、記載漏れの追記）で、ステップ・APIコントラクト・スキーマ・ACマッピングの変更を含まない場合は、再レビューを呼び出さず、修正された箇所を自分で読んで確認する。それ以外は`design-reviewer`を**再レビューモード**で呼び出す（前回のレポートのパスを渡し、各指摘の解消確認と変更箇所のレビューだけを行わせる。設計書全体の再レビューはさせない）。合計最大2回繰り返し、stateの`review retry`に記録する。
- 確度低の指摘には目を通し、実際の欠陥だと判断できるものは要修正に格上げする。
- 任意の指摘は修正モードの呼び出しに同じレポートで渡り、反映するかはアーキテクトが判断する。
- レポートに**要件への差し戻し候補**がある場合は、AskUserQuestion経由でユーザーに確認する。要件側を直すと決まったら、`requirements-analyst`を更新モードで`.scratch/<issue番号>/requirements.md`に対して呼び出し、`gh issue edit <issue番号> --body-file .scratch/<issue番号>/requirements.md`でIssue本文（正本）を同期してから、アーキテクトの修正モードに進む。
- 予算を使い切っても要修正が残る場合は、残った指摘をユーザーに要約し、そのまま実装に進むか中断するかをユーザーに決めてもらう。
- 差し戻しが発生した場合は、「Lessons learned」の形式でlessonエントリを追記する。

**設計の記録と確認。**

1. 設計内容をIssueに投稿する。見出し`## 設計`に`.scratch/<issue番号>/design.md`を続けて投稿する。このコメントが設計の正本となる。
2. ユーザーに短い要約（影響を受けるファイル + アプローチ、数文）を見せる。**confirm-design**モードでは、続行前にAskUserQuestion経由で承認を待つ。**auto**モードでは即座に続行する。この要約はゲートではなく状況報告である。
3. stateコメントを更新する。設計の記録はIssueコメントであるため、チェックポイントコミットは行わない。
