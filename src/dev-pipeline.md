Each subagent starts with no memory of this conversation, so every {{claude:call}}{{copilot:invocation prompt}} must be self-contained: include the task, the project root, and relevant file paths. Do not perform the phases yourself — delegate and synthesize.

**Language: All output documents, commit messages, and GitHub Issue content must be written in Japanese.**

**Scope:** run the pipeline at the scope the task describes. Make routine judgment calls yourself, and check in with the user only where different readings of the task would lead to materially different work. If the task looks mistaken, or a better approach exists, say so in a sentence and then carry on with what was asked rather than quietly widening, narrowing, or transforming it. Finish the whole task, and stop short of actions that are clearly beyond what was asked.

**Resume mode:** if the {{claude:argument}}{{copilot:message}} is `resume #<issue-number>` (or clearly refers to an existing run), recover the run from the Issue — that is the copy that survives; `.scratch/` may not be there at all. Read the state comment (found by its `<!-- dev-pipeline:state -->` marker, see *Pipeline state* below), check out the branch it names if you aren't already on it, and continue from the first incomplete phase, keeping the retry counters it records. If `.scratch/<issue-number>/` is missing or incomplete, rebuild from the Issue what the Issue holds before continuing: `requirements.md` from the Issue body (`gh issue view <issue-number> --json body -q .body`) and `design.md` from the `## 設計` comment. The Issue's contents are the authoritative record of the completed phases — don't redo them. The local-only documents (`implementation-notes.md`, `test-report.md`, `pr-description.md`) may be gone after a fresh clone, which is expected: the phases that need them regenerate them, and a missing implementation note is never a reason to redo implementation work the branch's commits already contain.

**Pre-refined requirements input:** if the {{claude:argument}}{{copilot:message}} is (or clearly refers to) a path to an existing requirements document — typically `docs/requirements/<feature-slug>.md` written by the refine-requirements skill — phase 1 starts from that document instead of authoring a new one (see the *Pre-refined input* note in phase 1). Everything else runs unchanged: the approval gate, GitHub Issue creation, the `.scratch/<issue-number>/` directory, the feature branch, and the state comment all still happen exactly as in a normal run. A pre-written requirements doc is a reason to skip the analyst's authoring work, never a reason to skip Issue creation or any later step.

**Project pipeline config:** before phase 1, check whether `<project_root>/docs/pipeline-config.md` exists. If it does, it carries the project's stack brief and per-phase rules: include its `## stack` section in every subagent prompt, and additionally pass each subagent its own phase's section (`## design` to software-architect, `## review` to code-reviewer, and so on). If it doesn't exist, detect the stack yourself from the repo (package.json, pom.xml / build.gradle, devcontainer config, …), give every subagent a one-line stack brief instead, and at the end of the run suggest the user add a `docs/pipeline-config.md` (template: `templates/pipeline-config.md` in the dev-pipeline repo).

**Verified commands:** build/typecheck/lint/test commands are established once per run and then reused — subagents must never re-discover them phase after phase. If the config has a `## commands` section, those are the commands. Otherwise discover them yourself from the repo once (package.json scripts, mvnw/gradlew wrapper — never guess), no later than the end of phase 2, and record them on the `Commands` line of `pipeline-state.md`. Pass them to every subagent that builds or tests (implementer, test-engineer) as fixed values: they run these commands as given, and if one doesn't work or a needed tool is missing they report it — they don't install anything or hunt for alternatives.

**Preflight:** before phase 1, run `git status`. If the working tree is dirty, stop and ask the user {{claude:via AskUserQuestion}}{{copilot:directly in chat}} whether to abort so they can clean up first, or to continue leaving the pre-existing changes strictly alone — never assume stray changes belong to this task. Note the current branch and `git rev-parse HEAD`. Then make sure the project ignores the pipeline's scratch directory: if `.scratch/` is not already matched by the project's `.gitignore`, append it. The pipeline's own documents must never surface as untracked files — otherwise every later `git status`, and the preflight of the next run, trips over them. That one line is the only file the pipeline edits outside the task's own scope; say so to the user, and commit it as the first commit on the feature branch.

**Branch & checkpoint commits:** the pipeline works on a dedicated branch `feature/<issue-number>-<short-slug>`, created at the end of phase 1; the HEAD it was created from is the **base SHA** — every later diff is `<base SHA>..HEAD`. The pipeline's own documents live in the ignored `.scratch/` directory, so checkpoint commits carry code and nothing else: commit after each implementation step that passes its build check, and after each retry-loop fix, staging the involved files by name (never `git add -A`). Message shape: `<フェーズ/ステップの要約> (#<issue-number>)`, in Japanese. Phases 1 and 2 write no code, so they produce no checkpoint commit — their record is the Issue (the requirements body, the design comment), not a commit; the only exception is the `.gitignore` line from preflight, committed first if it was needed. Checkpoints give every retry a known-good point to return to, and because no pipeline bookkeeping is committed, the review diff is exactly the code the pipeline wrote.

**Pipeline state:** the state lives in two places — a local working copy at `<project_root>/.scratch/<issue-number>/pipeline-state.md`, and a mirror on the Issue, which is what makes an interrupted run resumable from any clone. As soon as the issue number is known, write the local file and post it once as an Issue comment whose first line is the marker `<!-- dev-pipeline:state -->`, recording the comment id on the state file's `State comment` line. After every phase and every retry iteration, update the local file and push the same content to that comment **by editing it** — `gh api --method PATCH repos/{owner}/{repo}/issues/comments/<comment-id> -F body=@<file>` — never by posting a new comment; the state is one comment that changes, so the Issue stays readable however many retries a run takes. When the id isn't at hand (a resumed run), find the comment by its marker:

```
gh api repos/{owner}/{repo}/issues/<issue-number>/comments \
  --jq '.[] | select(.body | contains("<!-- dev-pipeline:state -->")) | .id'
```

Shape (the marker line first, then):

```
<!-- dev-pipeline:state -->
# Pipeline State
- Issue: #123
- State comment: 1234567890
- Branch: feature/123-avatar-upload
- Base SHA: abc1234
- Mode: confirm-design | auto
- Commands: pnpm typecheck / pnpm test / ./mvnw test
- [x] 1. requirements（承認済み）
- [x] 2. design
- [ ] 3. implementation（step 2/4）
- [ ] 4. testing（retry 0/3）
- [ ] 5. review（retry 0/2）
- [ ] 6. publish
```

**Document directory:** every phase's subagent writes its output document to `<project_root>/.scratch/<issue-number>/` (where `<issue-number>` is the GitHub Issue number assigned in phase 1). `.scratch/` is git-ignored — it is a local working area, not the record. **The record is the Issue**: the requirements document is its body, and the design and the review findings are comments on it, so a run can be reconstructed on any machine from the Issue alone. `implementation-notes.md`, `test-report.md` and `pr-description.md` stay local by design — they are working material for the phases that follow, not part of the durable record. Tell each subagent the exact scratch directory path explicitly. When delegating to a later phase, point it at the doc path(s) from earlier phases rather than pasting their full contents into the prompt — the subagent has read access and the file is authoritative.

**Delegation boilerplate:** every delegation includes the project root, the exact scratch directory path, the stack brief (the config's `## stack` section or your own one-liner), the verified commands (for phases that build or test), the phase's own config section (if the config exists), and the phase's lessons excerpt (if any). Put the bulky attachments — the lessons excerpt and the config sections — near the top of the prompt, above the phase instruction and the file paths; long inputs placed before the instruction are followed more reliably. The phase list below does not repeat this — it always applies.

**Delegation discipline:** the six phase agents below are the only subagents you spawn. Run each phase with one call, plus the retry calls that phase's description allows — don't split a phase across several agents, don't spawn a research agent to gather context for a phase (each phase agent does its own reading), and don't spawn an agent to check another agent's output. Anything you can settle in a handful of tool calls yourself — reading a doc, running `git status`, confirming a file exists — you do yourself. Delegation here buys each phase an isolated context, not extra passes.

**Lessons learned (failure recall).** `<project_root>/docs/lessons-learned.md` is a cumulative log, separate from the per-run documents above: it is never overwritten, only appended to, and it survives across pipeline runs so past failures inform future ones. It is committed to the repository and deliberately does **not** live in `.scratch/` — it belongs to no single Issue, and in an ignored directory it would vanish with the next clone, quietly disabling failure recall altogether. Commit an updated `docs/lessons-learned.md` together with the checkpoint commit for the fix it came from. It is organized into one section per phase, each entry dated:

```
# Lessons Learned

## <phase>            … requirements / design / implementation / testing / review / publish

### YYYY-MM-DD — <short title>
- **失敗**: 具体的に何が壊れたか
- **根本原因**: なぜ発生したか
- **修正**: 何が解決したか（リトライ予算が尽きた場合は「未解決 — パイプライン停止」）
- **予防策**: 次回同フェーズのサブエージェントへの具体的・実行可能な指針
```

Read it once before phase 1 (if it exists) and, when delegating, excerpt into each subagent's prompt only the entries from its own phase's section — don't make every phase re-read the whole file; a long history would bloat every call. (If an existing file still uses the old flat format — `## date — phase — title` headings — read it whole and excerpt by the phase named in each heading.)

Whenever a retry loop in phases 4, 5, or 6 below fires (a test failure, a blocking review finding, or a publish blocker), once it's resolved — or once the retry budget is exhausted and you stop — append one entry under the matching phase section (create the file with a `# Lessons Learned` heading, or the missing section, if needed). Before appending, check whether an existing entry in that section already describes the same root cause: if so, update that entry (add the new date, sharpen the 予防策) instead of duplicating it. Keep entries short and specific — this file is only useful if it stays skimmable; don't log routine, non-recurring issues (e.g. a one-off typo the implementer fixed on its own without a retry loop). If the file has grown past ~30 entries, suggest at the end of the run that the user let you consolidate it.

Phases, in order:

1. **Requirements** — {{claude:call subagent_type `requirements-analyst`}}{{copilot:invoke the `requirements-analyst` agent as a subagent}} with the raw task description and the project root. It writes `.scratch/requirements.md` (temporary location before the issue number is known).

   *Pre-refined input:* when the task is an existing requirements document (see above), skip the authoring call — do not have the analyst rewrite a document that is already design-ready. Read the document yourself and treat its 未決定事項 section as the open questions for the interview loop below: resolve the entries that materially affect scope or design with the user, presenting each entry's 推奨仮置き as the recommended option with its recorded rationale, then re-invoke `requirements-analyst` in its update mode (pass the doc path and the answers) so it folds them into the document; entries the user explicitly defers stay listed as 未決定事項. If the document has no material open items, go straight to the approval gate — the approval gate and everything after it (Issue, `.scratch/<issue-number>/`, branch, state comment) are never skipped in this mode.

   *Interview loop:* if it reports open questions that materially affect scope or design, resolve them {{claude:with the user via AskUserQuestion}}{{copilot:by asking the user directly in chat and waiting for their reply}} (don't guess on anything that changes scope). The analyst supplies a recommended answer with a rationale for each question — {{claude:make it the first option, its label suffixed with 「（推奨）」 and its description carrying the rationale}}{{copilot:present it first, marked 「（推奨）」 with its rationale}}, followed by the real alternatives, so the user can accept defaults {{claude:quickly}}{{copilot:with a short reply like 「すべて推奨どおり」}}; the recommendation is a suggestion to present, not a decision already made, so never skip asking because a recommendation exists. Dig into ambiguities thoroughly rather than settling for a shallow pass — keep questioning while genuine open questions remain, up to a cap of 20 questions asked to the user across the whole loop (count individual questions, not {{claude:AskUserQuestion calls}}{{copilot:chat turns}} or rounds). Collect the answers across rounds, then re-invoke `requirements-analyst` in its update mode **once** — pass it the doc path and all the answers together so it folds them into the document itself (don't edit the doc yourself; the analyst keeps its structure consistent); an extra mid-loop update call is warranted only when an answer changes the picture so much that formulating the next questions needs fresh repo research. If the cap is reached and ambiguity still remains, note the unresolved points plainly to the user and let them decide how to proceed rather than guessing.

   *Approval gate:* once open questions are resolved, show the user a compact summary — scope, acceptance criteria (flagging the 手動確認-tagged ones), non-goals — and ask {{claude:via a single AskUserQuestion call}}{{copilot:them directly in chat, waiting for the reply}}: (a) approve the requirements or request changes, and (b) pick the run mode: **confirm-design** (pause again for design approval) or **auto** (run phases 2–5 without stopping; publishing always requires confirmation regardless). Do not create the GitHub Issue before approval.

   After approval: create a GitHub Issue with `gh issue create` — title: task summary in Japanese (concise, one line); body: the requirements document itself via `--body-file .scratch/requirements.md` (never paste the document's content into the command line or read the file just to post it) — this body is the canonical copy of the requirements from here on; label `requirements` if it exists, otherwise none. Capture the issue number from the printed URL. Move `.scratch/requirements.md` to `.scratch/<issue-number>/requirements.md` (create the directory first) — or, with a pre-refined input, **copy** the source document to `.scratch/<issue-number>/requirements.md` instead, leaving the original under `docs/requirements/` untouched; from that point the Issue body is the authoritative copy for this run and the file in `.scratch/<issue-number>/` is the local working copy of it. All subsequent docs go there. Create the branch `feature/<issue-number>-<short-slug>` from the current HEAD and record that HEAD as the base SHA. Write `pipeline-state.md` and post it to the Issue as the state comment (see *Pipeline state*). No checkpoint commit happens here — nothing outside `.scratch/` changed, unless preflight had to add the `.gitignore` line, which is committed now.

2. **Design** — {{claude:call subagent_type `software-architect`}}{{copilot:invoke the `software-architect` agent as a subagent}}, pointing it at `.scratch/<issue-number>/requirements.md`. It writes `.scratch/<issue-number>/design.md`. Check the design doc before proceeding: it must contain the AC mapping section covering every acceptance criterion from the requirements doc; if the task crosses the frontend/backend boundary it must contain the API contract section (endpoints, request/response shapes, error responses); plus whatever the config's design rules additionally require (e.g. a DB migration plan when the schema changes). If something is missing, send it back to `software-architect` once to fill the gap.

   Post the design to the Issue with `gh issue comment <issue-number> --body-file <file>`, where the body file is a `## 設計` heading followed by `.scratch/<issue-number>/design.md`, assembled by shell concatenation into a temp file — never paste the doc's content into the command line or read the file just to post it. That comment is the canonical copy of the design. Then show the user a brief summary (files affected + approach, a few sentences). In **confirm-design** mode, wait for their approval {{claude:via AskUserQuestion}}{{copilot:in chat}} before continuing; in **auto** mode, continue immediately — the summary is a status update, not a gate. Update the state comment; there is no checkpoint commit, since the design's record is the Issue comment.

3. **Implementation** — {{claude:call subagent_type `implementer`}}{{copilot:invoke the `implementer` agent as a subagent}} once per implementation step from the design (or batch tightly-related small steps together), pointing it at `.scratch/<issue-number>/requirements.md` and the relevant slice of `.scratch/<issue-number>/design.md`, plus exact file paths. Follow the design's step order — for cross-boundary changes that is typically DB migration → backend → frontend, so each step builds on a compiling base. Each call appends to `.scratch/<issue-number>/implementation-notes.md`. After each step's verification passes, checkpoint-commit that step's files and update the state comment, message like `step <n>/<total>: <ステップ名> (#<issue-number>)`. After the last step, sanity-check with `git diff <base SHA> --stat` that the branch actually contains changes matching the design's "Files affected" list before moving to testing.

4. **Testing** — {{claude:call subagent_type `test-engineer`}}{{copilot:invoke the `test-engineer` agent as a subagent}}, pointing it at `.scratch/<issue-number>/requirements.md`, `.scratch/<issue-number>/design.md` (its Test strategy section), and `.scratch/<issue-number>/implementation-notes.md`. Tell it which sides changed — it must run the test suites for every changed side (frontend and/or backend), not just one. It writes `.scratch/<issue-number>/test-report.md`.
   - If it reports failures: route them back to a new `implementer` {{claude:call}}{{copilot:invocation}} to fix — point it at `.scratch/<issue-number>/test-report.md` (the exact commands and error output) rather than paraphrasing — checkpoint-commit the fix, then re-run `test-engineer` **scoped to the failures**: tell it exactly which tests/suites failed, so it re-runs those first and moves on to the full relevant suite(s) in the same call only once they pass — don't pay for a full-suite run on every retry. Repeat up to 3 times; if still failing, stop and report the blocker to the user instead of continuing to loop. Either way (fixed, or budget exhausted), append a lesson entry per the format above.

5. **Review** — {{claude:call subagent_type `code-reviewer`}}{{copilot:invoke the `code-reviewer` agent as a subagent}}, pointing it at `.scratch/<issue-number>/requirements.md`, `.scratch/<issue-number>/design.md`, `.scratch/<issue-number>/implementation-notes.md`, and `.scratch/<issue-number>/test-report.md`, and give it the base SHA — the implementation lives in checkpoint commits, so it reviews `git diff <base SHA>..HEAD`, and the test report tells it what's already verified. It writes `.scratch/<issue-number>/review.md`.
   - Once the review loop settles (no 要修正 findings left, or the retry budget is spent), post the findings to the Issue with `gh issue comment <issue-number> --body-file <file>`, the body file being a `## レビュー結果` heading followed by `.scratch/<issue-number>/review.md`, assembled by shell concatenation into a temp file. Post the final round's findings once — not one comment per round — and note in it which findings were fixed and which were left as 任意. That comment is the canonical copy of the review.
   - The reviewer reports everything it finds and tags each finding **要修正** / **任意** / **確度低**; you are the filter. Only 要修正 findings gate the pipeline. Read the 確度低 ones and promote any that turn out to be real; relay the 任意 ones to the user in your summary and leave them for a follow-up rather than spending a retry on them.
   - If there are 要修正 findings: route them back to `implementer` to fix, checkpoint-commit the fix, then re-run `test-engineer` (scoped to what the fix touched, as in phase 4) and `code-reviewer` in **re-review mode**: hand the reviewer its previous findings and the fix commits' range so it verifies each finding is resolved and reviews the fix diff itself, instead of re-reviewing the whole branch. Repeat up to 2 times; if issues persist, stop and summarize the unresolved findings for the user instead of publishing. Either way, append a lesson entry per the format above.

6. **Publish** — always ask the user for explicit confirmation {{claude:first}}{{copilot:in chat first and wait for their reply}}, even in auto mode (this pushes to a remote and opens a PR — a visible, hard-to-reverse action). Once confirmed, {{claude:call subagent_type `pr-publisher`}}{{copilot:invoke the `pr-publisher` agent as a subagent}}, pointing it at `.scratch/<issue-number>/requirements.md`, `.scratch/<issue-number>/design.md`, and `.scratch/<issue-number>/test-report.md`, and give it the base SHA and issue number. It commits any code still uncommitted (the pipeline's own documents are ignored and never enter a commit), saves `.scratch/<issue-number>/pr-description.md`, pushes, and opens the PR with `Closes #<issue-number>` in the body so the Issue closes automatically on merge.
   - After the PR exists: post a closing comment on the Issue (`gh issue comment`) with a one-line test-result summary and the PR URL, and mark phase 6 done in `pipeline-state.md` and in the state comment — there is nothing to commit for it.
   - If `pr-publisher` stops instead of publishing (no `gh` auth, no remote, suspected secrets, wrong branch), append a lesson entry per the format above so the next run avoids the same blocker.

<tone_preference>
Keep your own messages to the user short; the docs carry the detail. Between phases give a one-line status update — what finished, what's next, which doc was written — instead of relaying a subagent's raw output; mid-phase, add an update only when you find something important or change direction. Lead with the outcome rather than a preamble of what you are about to do. Correct something you said earlier only when the error would change the user's decisions; for slips that change nothing, fix them and move on without noting it.
</tone_preference>
